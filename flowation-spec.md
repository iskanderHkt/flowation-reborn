# Flowation — Техническое задание

> Платформа тестовой автоматизации API.  
> Архитектура: модульный монолит.

---

## 1. Что такое Flowation

Flowation позволяет тестировать API без написания кода. Пользователь собирает тесты из готовых блоков, запускает их и видит результат в реальном времени.

**Основные сущности:**

- **Операция** — атомарный шаг: HTTP-запрос, SQL-запрос или проверка (assert)
- **Флоу** — цепочка операций, выполняемых последовательно. Флоу могут вкладываться друг в друга (до 5 уровней)
- **Окружение** — именованный набор переменных (base_url, api_key и т.д.), который подставляется в операции при запуске
- **Батч** — параллельный запуск нескольких флоу одной кнопкой

---

## 2. Зачем переписывать

Текущая версия — распределённая система из 5 компонентов: Java API-сервер, Go воркер, RabbitMQ, Redis, Postgres. Для solo-разработчика это означает:

- Два языка, две системы сборки, два рантайма
- Три инфраструктурных сервиса вместо одного
- Docker Compose обязателен даже для локальной разработки
- Дебаг распределённых ошибок при отсутствии реальной нагрузки, оправдывающей такую архитектуру

**Цель:** один бэкенд-процесс, одна внешняя зависимость (Postgres), тот же функционал. Запуск в два шага: `backend` и `frontend`.

---

## 3. Что должна уметь система

### 3.1 Управление операциями

Пользователь создаёт, редактирует, удаляет операции трёх типов:

- **HTTP-запрос** — метод, URL, заголовки, тело. Поддержка переменных в любом поле через синтаксис `{{переменная}}`
- **SQL-запрос** — строка подключения, запрос. Поддержка PostgreSQL и MySQL
- **Assert** — проверка значения из контекста выполнения (равенство, содержание, регулярное выражение и т.д.)

Каждая операция имеет шаблон конфигурации (`configTemplate`), который может быть переопределён при включении в флоу.

### 3.2 Управление флоу

Флоу — упорядоченная последовательность шагов. Каждый шаг ссылается на операцию или на другой флоу (вложенность). Визуальный редактор на фронтенде позволяет собирать флоу drag-and-drop.

При запуске вложенные флоу рекурсивно разворачиваются в плоский список шагов. Система обнаруживает циклические ссылки и блокирует их.

### 3.3 Окружения

Набор key-value переменных. При запуске флоу пользователь выбирает окружение, и все `{{переменные}}` резолвятся из него. По мере выполнения шагов контекст обогащается: extraction rules вытаскивают значения из ответов и делают их доступными для следующих шагов.

### 3.4 Выполнение

Три режима запуска:

| Режим | Что запускается | Поведение |
|-------|----------------|-----------|
| Instant | Одна операция | Выполнить и вернуть результат |
| Flow | Один флоу | Последовательно выполнить все шаги |
| Batch | Несколько флоу | Запустить параллельно, агрегировать результаты |

Каждое выполнение сохраняется в БД со статусом, временем, результатами каждого шага.

### 3.5 Прогресс в реальном времени

Браузер подписывается на SSE-поток и получает события по мере выполнения: старт, завершение каждого шага, итоговый статус. Пользователь видит прогресс без перезагрузки страницы.

### 3.6 Аутентификация

JWT-аутентификация. Регистрация, логин, автообновление токена на фронтенде.

## 4. Архитектурные принципы

### 4.1 Модульный монолит

Один бэкенд-процесс, внутри которого логика разделена на изолированные модули. Каждый модуль:

- Владеет своими данными (таблицами) и не обращается к чужим таблицам напрямую
- Предоставляет публичный интерфейс, через который другие модули могут запрашивать данные
- Скрывает внутреннюю реализацию — контроллеры, сервисы, репозитории модуля невидимы извне

**Модули:**

| Модуль | Зона ответственности |
|--------|---------------------|
| auth | Регистрация, логин, JWT |
| flow | CRUD операций и флоу |
| environment | CRUD окружений и переменных |
| execution | Компиляция, запуск, выполнение шагов, SSE-прогресс, сохранение результатов |
| shared | Общие типы, события, утилиты (минимум) |

### 4.2 Замена инфраструктуры на in-process аналоги

| Было | Стало | Принцип |
|------|-------|---------|
| RabbitMQ (очереди задач) | Пулы потоков с ограниченной очередью | Backpressure через размер очереди, при переполнении — отказ с кодом 429 |
| Redis pub/sub (прогресс) | Прямая отправка SSE-событий из executor-а | Нет промежуточного хранилища, нет сериализации |
| Go worker (исполнение шагов) | Java-модуль в том же процессе | Те же типы операций, та же логика, другой язык |
| JSON Schema контракты | Типизированные интерфейсы между модулями | Компилятор проверяет совместимость |

### 4.3 Три пула исполнения

Для сохранения изоляции между режимами запуска (как было с разными очередями в RabbitMQ), бэкенд поддерживает три раздельных пула потоков: для instant, flow и batch. Размеры настраиваются через конфигурацию.

### 4.4 Межмодульное взаимодействие

Два способа:

- **Запрос данных** — модуль вызывает публичный интерфейс другого модуля. Например, execution запрашивает у flow структуру флоу для компиляции
- **Уведомления** — модуль публикует событие (например, «выполнение завершено»), подписчики реагируют. Для односторонних оповещений, не для запросов данных

### 4.5 Готовность к будущему разделению

Модульные границы проектируются так, чтобы при необходимости любой модуль можно было выделить в отдельный сервис. Замена in-process очереди на RabbitMQ или прямого SSE на Redis pub/sub — точечное изменение за одним интерфейсом, не затрагивающее бизнес-логику.

## 5. Пользовательский опыт

Фронтенд не меняется. Те же экраны, тот же визуальный редактор, тот же SSE-прогресс. REST API сохраняет все текущие эндпоинты и форматы ответов.

**Ключевые эндпоинты (без изменений):**

- Аутентификация: `/api/auth/login`, `/api/auth/register`
- Операции: `/api/operations/**`
- Флоу: `/api/flows/**`
- Окружения: `/api/environments/**`
- Запуск: `/api/operations/{id}/execute`, `/api/flows/{id}/execute`, `/api/batch/execute`
- Результаты: `/api/executions/{id}`
- SSE-поток: `/api/executions/{id}/stream`

## 6. Запуск и деплой

### Локальная разработка

Требования: Java 21+, Node.js 20+, PostgreSQL (локальный или один Docker-контейнер).

```
# Бэкенд
cd backend && ./gradlew bootRun

# Фронтенд
cd frontend && npm run dev
```

Никакого Docker Compose с пятью сервисами. Никакого Go. Никакого RabbitMQ и Redis.

### Продакшен

Один JAR-файл + Postgres. Фронтенд-билд отдаётся через встроенный веб-сервер или через Nginx.

## 7. Что удаляется из репозитория

| Директория | Причина |
|------------|---------|
| `worker-engine/` | Логика переносится в модуль execution |
| `infra/` | Docker Compose больше не нужен (или сокращается до одного Postgres) |
| `contracts/` | JSON Schema заменяются типизированными интерфейсами внутри кода |

## 8. План реализации

### Этап 1 — Скелет
Структура проекта, модульные пакеты, миграции БД, архитектурные тесты на границы модулей.

### Этап 2 — Auth + CRUD
Модули auth, flow, environment. REST API с теми же эндпоинтами. Фронтенд переключается на новый бэкенд.

### Этап 3 — Исполнение
Модуль execution: компиляция флоу, step handlers (HTTP, SQL, Assert), пулы потоков, SSE-прогресс, сохранение результатов.

### Этап 4 — Batch + финализация
Логика батч-запуска, E2E-тесты, удаление старых директорий, обновление документации.

---

## 9. Критерии готовности

- Все текущие API-эндпоинты работают с теми же контрактами
- Фронтенд работает без изменений
- Запуск операции, флоу и батча даёт те же результаты
- SSE-прогресс отображается в реальном времени
- Бэкенд запускается одной командой без внешних сервисов кроме Postgres
